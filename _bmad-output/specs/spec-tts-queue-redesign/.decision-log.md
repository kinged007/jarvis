## 2026-06-06 — Implementation + extensions

**Implemented (CAP-1 through CAP-5):**
- `bridge.ts`: `reasoning.available` enqueues commentary text to TTS; `flushResponseDelta` uses `enqueue()` (single utterance) instead of `enqueueText()` (sentence-split); sentence boundary finder removed.
- `queue.ts`: Defaults to Deepgram REST (confirmed in logs; no WS provider constructed).
- `bridge.test.ts`: Updated to assert commentary IS enqueued and response is a single utterance.
- All 28 tests pass; TypeScript clean; demo.mjs confirms pipeline end-to-end.

**Extensions beyond initial SPEC:**

1. `tts:queue` message (shared protocol `ServerTtsQueue`, BFF queue broadcasts, demo client display): gives the client a live, updating queue view — items in order, ▶ indicator for the currently-synthesizing utterance. Sent on every enqueue / synthesis-start / completion / clear.

2. `TTS_COMMENTARY_ENABLED` env var (default `true`): gates the commentary TTS enqueue in the bridge. Added to `env.ts`, threaded through `BffAgentServiceDeps` → `BridgeOptions`. When `false`, commentary is still broadcast as text but not voiced — addressing the Hermes echo concern (response text emitted on both channels).

**Open question resolved:** Commentary TTS is configurable via `TTS_COMMENTARY_ENABLED=false` in `.env`. Default is `true` (voiced) per CAP-1.
