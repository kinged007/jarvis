# Hermes Runs API Event Vocabulary

The canonical BFF ↔ Hermes boundary. Source of truth: `gateway/platforms/api_server.py` lines 3486-4041 (`_make_run_event_callback`, `_handle_runs`, `_handle_run_events`, `_handle_run_approval`, `_handle_stop_run`).

## Endpoint surface

| Method | Path | Auth | Purpose | BFF usage |
|---|---|---|---|---|
| `GET` | `/health` | none | `{status:"ok"}` liveness | spawner polls until ready |
| `GET` | `/health/detailed` | none | full gateway state | optional, for `/api/agent/status` |
| `GET` | `/v1/capabilities` | Bearer | machine-readable API surface | cached at startup, used for `api.model` |
| `POST` | `/v1/runs` | Bearer | start a run, returns 202 with `run_id` | `runTracker.submit(input, previousResponseId)` |
| `GET` | `/v1/runs/{run_id}` | Bearer | pollable run status | debug/diagnostics only |
| `GET` | `/v1/runs/{run_id}/events` | Bearer | SSE stream of lifecycle events | `runTracker.subscribe(runId)` |
| `POST` | `/v1/runs/{run_id}/stop` | Bearer | interrupt a running agent | `runTracker.stop(runId)` (called on WS `cancel`) |
| `POST` | `/v1/runs/{run_id}/approval` | Bearer | resolve a pending approval | `runTracker.respondApproval(runId, choice)` |

### Auth header

Every authenticated request:
```
Authorization: Bearer ${HERMES_API_KEY}
Content-Type: application/json
```

The BFF reads `HERMES_API_KEY` from the BFF's `.env` at startup and includes it in every request via the shared `apiClient` instance.

## `POST /v1/runs` request body

```jsonc
{
  "input": "user message text",   // string OR array of {role, content} messages
  "previous_response_id": "resp_abc...",  // optional, for conversation continuity
  "session_id": "jarvis:bff:user-1",  // optional, overrides default
  "instructions": null,            // optional, ephemeral system prompt override
  "model": "jarvis"                // optional, defaults to the advertised model
}
```

The BFF submits:
- `input`: a single string (the text from the WS `command` or the final STT transcript)
- `previous_response_id`: the cached `response_id` from the last `run.completed` on the same WS, if any
- `session_id`: a stable per-WS-connection id (e.g. `jarvis:ws:<uuid>`)
- everything else omitted (the agent's default model + system prompt apply)

### Response (202 Accepted)

```json
{ "run_id": "run_abc123...", "status": "started" }
```

The `run_id` is what the BFF uses to subscribe to `/v1/runs/{run_id}/events` and to call `/stop` and `/approval`.

## SSE event vocabulary

The API server emits events as `data: <json>\n\n` on the SSE stream. A `None` sentinel closes the stream. The BFF parses with `eventsource-parser` and dispatches to the bridge.

### `message.delta`

Streamed response text. This is the actual answer text being generated by the LLM, fed character-by-character (well, token-by-token, but framed as deltas) to the TTS queue.

```json
{ "event": "message.delta", "run_id": "run_...", "timestamp": 1234567890.123, "delta": "the weather in Tokyo is" }
```

**BFF → WS:** `agent:response_delta` (new type, see `ws-message-changes.md`)

**BFF logging:** `debug` level (text is never logged).

### `tool.started`

A tool is being invoked.

```json
{ "event": "tool.started", "run_id": "run_...", "timestamp": 1234567890.123, "tool": "web_search", "preview": "searching for weather in Tokyo" }
```

**BFF → WS:** `agent:tool_call` (extended with `preview?: string`).

**BFF logging:** `info` level.

### `tool.completed`

A tool finished.

```json
{ "event": "tool.completed", "run_id": "run_...", "timestamp": 1234567890.123, "tool": "web_search", "duration": 1.234, "error": false }
```

**BFF → WS:** `agent:tool_result` (extended with `duration?: number` and `error?: boolean`).

**BFF logging:** `info` level.

### `reasoning.available`

Thinking/reasoning text from the LLM (e.g. when the model is "thinking out loud" before the answer). This is **not** the streamed response — it's the model's internal monologue / planning. The BFF treats it as `commentary` (preamble, not spoken aloud in the JARVIS voice flow).

```json
{ "event": "reasoning.available", "run_id": "run_...", "timestamp": 1234567890.123, "text": "I need to look up the weather in Tokyo..." }
```

**BFF → WS:** `agent:commentary` (existing type).

**BFF logging:** `info` level.

### `approval.request`

The agent is asking for human approval before executing a tool. Sent when YOLO mode is off or when the tool is in the manual-approval list.

```json
{
  "event": "approval.request",
  "run_id": "run_...",
  "timestamp": 1234567890.123,
  "request_id": "apr_abc...",        // Hermes-internal id
  "tool": "browser_navigate",
  "args": { "url": "https://..." },
  "message": "About to open browser to https://...",
  "choices": ["once", "session", "always", "deny"]
}
```

**BFF → WS:** `agent:approval_request` (new type, see `ws-message-changes.md`).

**BFF logging:** `info` level. Run status flips to `waiting_for_approval` server-side.

### `approval.responded`

An approval request was resolved (either by the BFF, or by another path).

```json
{ "event": "approval.responded", "run_id": "run_...", "timestamp": 1234567890.123, "choice": "once", "resolved": 1 }
```

**BFF → WS:** `agent:approval_resolved` (new, informational). Run status flips back to `running`.

**BFF logging:** `info` level.

### `run.completed`

The run finished successfully. The terminal event.

```json
{
  "event": "run.completed",
  "run_id": "run_...",
  "timestamp": 1234567890.123,
  "output": "The full final response text, same as the concatenation of message.delta frames.",
  "usage": { "input_tokens": 1234, "output_tokens": 567, "total_tokens": 1801 }
}
```

**BFF → WS:** synthesized terminal `agent:response` (with the full `output` text) + `system:status {agentReady: true}`. The BFF also caches the `response_id` (carried in the run's pollable status, not in this event) for the next `previous_response_id`. The cached id comes from `GET /v1/runs/{run_id}` after the run completes, OR — simpler — we use the `run_id` as a chain handle in v1 since the `previous_response_id` machinery is opaque to the BFF. **For v1: BFF sends `run_id` as `previous_response_id`** (Hermes accepts the same id namespace internally). Revisit if the chain breaks.

Wait — re-reading the API server: `previous_response_id` is set via the `ResponseStore` keyed on a `response_id` (different from `run_id`). The `run_id` is a higher-level handle. For correctness, the BFF should call `GET /v1/runs/{run_id}` after `run.completed` to fetch the actual `response_id` and use that for `previous_response_id` on the next run. See `subprocess-lifecycle.md` § "Previous response id handling" for the full procedure.

**BFF logging:** `info` level. Run status flips to `completed`.

### `run.failed`

The run errored.

```json
{ "event": "run.failed", "run_id": "run_...", "timestamp": 1234567890.123, "error": "agent run failed: ..." }
```

**BFF → WS:** `server:error {message: error}` + `system:status {agentReady: true}` (BFF still up).

**BFF logging:** `warn` level.

### `run.cancelled`

The run was interrupted (via `POST /v1/runs/{id}/stop`).

```json
{ "event": "run.cancelled", "run_id": "run_...", "timestamp": 1234567890.123 }
```

**BFF → WS:** `server:error {message: "cancelled"}` (matches the existing sidecar cancel behavior).

**BFF logging:** `info` level.

### `run.stopping`

A stop was requested, the run is winding down.

```json
{ "event": "run.stopping", "run_id": "run_...", "timestamp": 1234567890.123 }
```

**BFF → WS:** silent (debug log only). The BFF already acked the WS `cancel` and the user is informed via the `server:error {message:"cancelled"}` that follows when `run.cancelled` arrives.

**BFF logging:** `debug` level.

## Auth failure handling

`401` from the API server means the BFF's `HERMES_API_KEY` doesn't match the profile's `platforms.api_server.key`. The BFF:
1. Logs a `error` event with the API URL and a sanitized redacted-token marker.
2. Stops the subprocess (a 401 means setup is misconfigured; recovery requires a key rotation).
3. Surfaces `server:error {message: "agent authentication failed — check HERMES_API_KEY"}` to all active WS clients.
4. Backs off restart for 30s (longer than the normal backoff) to avoid a hot loop on a bad config.

## Error response shape (OpenAI-style)

All non-2xx responses from the API server use:
```json
{ "error": { "message": "...", "type": "invalid_request_error", "code": "rate_limit_exceeded", "param": "..." } }
```

The BFF extracts `error.message` and forwards it to the WS client in `server:error`. The `code` is logged at `warn` level.

## Concurrency cap

`_MAX_CONCURRENT_RUNS = 10` on the API server. A `429` with `code: "rate_limit_exceeded"` means too many concurrent runs. The BFF surfaces as `server:error` and does not retry.

## Orphan sweep

The API server sweeps orphaned (never-consumed) SSE streams every 60s after a 300s TTL (`_RUN_STREAM_TTL`). The BFF mitigates by always opening the SSE stream immediately after `POST /v1/runs` returns — the race window is < 50ms.
